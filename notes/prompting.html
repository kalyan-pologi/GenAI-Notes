✍️ Prompt Engineering

Techniques for writing prompts that reliably produce the output you want.

✍️ Core Concept

Why It Matters

The exact same model, same weights, same everything, can produce wildly different quality output depending purely on how the request is phrased. This is the entire premise of prompt engineering: the model is a capability, the prompt is what unlocks how much of it you actually get.
A vague ask forces the model to guess your intent, format, and scope, and it will guess wrong at least some of the time. A precise ask removes that guesswork entirely.
Prompting is cheap to iterate on compared to fine-tuning or switching models, which is why it is almost always the first lever to pull when output quality is disappointing.

Core Techniques

Be specific and explicit about format, length, tone, and constraints. "Summarize this" and "summarize this in 3 bullet points, under 20 words each, no jargon" produce very different reliability.
Provide context and examples. Showing the model one or two examples of the input-output pattern you want (few-shot prompting, covered on its own page) resolves ambiguity that no amount of description alone can.
Use role or persona framing ("you are a senior security reviewer") to steer tone, vocabulary, and the assumptions the model brings, though it is not a substitute for explicit constraints.
Break complex tasks into explicit steps rather than asking for the end result in one shot; this both improves reasoning and makes intermediate output easier to check.
Give the ideal output structure or schema upfront (a template, a JSON shape, a heading outline) so the model fills in a known container instead of inventing its own structure.

Iteration & Negative Constraints

Prompting is rarely a one-shot activity. Treat a prompt like code: write it, run it, look at where the output goes wrong, and revise the specific instruction that caused that failure.
Negative constraints ("don't use markdown", "don't mention pricing") are useful but often less reliable than positive instructions, because the model has to actively suppress a behavior rather than simply follow a directive. Telling it what to do instead ("respond in plain prose" rather than "don't use markdown") usually works better.
Stacking too many negative constraints without positive alternatives tends to produce stilted or overly hedged output, since the model is spending effort avoiding things rather than confidently doing something.
🔬 Deeper Look

Common Failure Patterns

Vague asks: "make this better" or "improve this code" give the model no criteria to optimize for, so it picks arbitrary ones that may not match what you actually wanted.
Contradictory instructions: asking for "a concise but comprehensive report" or "formal but casual tone" forces the model to silently resolve a conflict you never noticed you created.
Burying the actual question: pasting a wall of background material and tacking the real ask onto the end (or worse, the middle) risks the specific question getting under-weighted relative to the surrounding noise.
All three failure patterns share a root cause: the prompt describes the situation but not the decision criteria the model should use to produce good output.

Prompt Structure Best Practices

Separate instructions from data. Mixing "here is what to do" with "here is the content to do it on" in one undifferentiated blob makes it easy for the model to misread which part is which, especially with long inputs.
Use delimiters or XML-style tags (`...`, `...`) to mark section boundaries explicitly. This is one of the most reliable ways to keep long, multi-part prompts unambiguous.
For long prompts, put the most critical instructions near the end, right before the model starts generating. Models tend to weight recent context more heavily (a recency effect related to the lost-in-the-middle problem covered on the context window page), so the final instruction is the one most likely to be followed precisely.

Systematic Testing

Do not tune a prompt against a single example and assume it generalizes. Build a small set of representative test cases, including edge cases, and check the prompt against all of them before treating it as done.
Changing a prompt to fix one failing case can silently break a previously-working case; a lightweight eval set catches this the same way unit tests catch regressions in code.
For anything going into production, this systematic pass matters far more than any single clever wording, because the real question is not "does this work once" but "does this work reliably across the range of inputs it will actually see."
🎯 Applying It

One-off vs. Reusable Prompts

One-off prompting (asking a question in a chat interface) can afford to be loose and conversational, since you are right there to notice a bad answer and rephrase immediately.
Reusable prompt templates or system prompts for an application have to hold up across thousands of unseen inputs without a human in the loop to catch drift, so they need explicit structure, defined edge-case handling, and a way to be tested and versioned like any other piece of the system.
A system prompt for an application is closer to writing a spec than writing a question: it has to anticipate variation in user input that a single one-off prompt never has to consider.

Anti-Patterns

Overly long prompts that pile on caveats and context dilute the signal; the model has to sift through everything to find what actually matters for this specific request.
Contradicting instructions buried in different parts of a long prompt (common when a prompt has been edited many times by different people) force the model to pick a winner silently and unpredictably.
No examples for ambiguous formats: if there are multiple reasonable ways to interpret "list the key points," and the exact format matters, a single example resolves it far more reliably than more prose description would.

Practical Playbook

Start specific: name the format, length, audience, and tone explicitly rather than assuming the model will infer them correctly.
Add one or two examples the moment output format matters and prose description alone leaves room for interpretation.
Use delimiters or tags once a prompt has more than one distinct section (instructions, data, examples, output format).
Put the single most important instruction last for long prompts, and test against a small representative set before shipping.
⚠️ Reliability

Failure Modes

Prompt drift: a prompt tuned carefully against today's model version can behave differently after a silent model update, since providers periodically retrain or adjust models behind the same name.
Instruction dilution: as a prompt grows over time with patches for edge cases, the original core instruction can get buried under accumulated caveats, weakening the exact behavior it was meant to enforce.
Format non-compliance: even with an explicit schema, models can occasionally drift from the requested structure on edge-case inputs, which is why production systems validate output rather than trusting the prompt alone.
Over-reliance on negative constraints: stacking "don't do X" instructions without positive guidance tends to degrade rather than improve compliance.

Where It Fits

Prompt engineering is the layer that sits directly between the application and the model: it is the interface contract that determines what the model receives and, in large part, what shape of answer comes back.
It works alongside, not instead of, other levers: temperature and sampling parameters affect randomness, retrieval affects what facts are available, and prompting affects how the task itself is framed. Good prompting cannot fix missing context, and good retrieval cannot fix a poorly framed instruction.
Prompting is the cheapest, fastest lever to pull before reaching for fine-tuning, a bigger model, or new tooling.

Real World Example

A support-ticket triage system uses a system prompt with explicit XML-tagged sections: `` listing valid labels, `` showing three labeled tickets, and `` holding the actual input, with the final instruction ("respond with only the category name") placed last.
When misclassification rates crept up after a model upgrade, the fix was re-running the existing eval set of labeled tickets against the new model version and adjusting the category examples, not rewriting the prompt from scratch.
Treating the prompt as a versioned, tested artifact rather than a one-time piece of text is what made the failure fast to diagnose and cheap to fix.
