Foundations

🧠 LLMs & How They Work

What a large language model actually is, and how it generates text.

🧠 Core Concept

What It Actually Is

At its core, an LLM is a next-token predictor. Given a sequence of tokens, it outputs a probability distribution over what token comes next, and text generation is just repeatedly sampling from that distribution.
The weights are a form of lossy compression of a huge slice of the internet. A ~1TB text corpus gets compressed into a few hundred GB of parameters, so the model has absorbed statistical patterns of the training data without literally storing it.
There is no separate "reasoning module" or database of facts. Everything the model does, from writing code to explaining physics, emerges from the single task of predicting the next token well.
This means the model is fundamentally a simulator of the text distribution it was trained on. It doesn't "know" it's an AI assistant until later training stages teach it to play that character.

Why This Approach

Predicting the next token is a self-supervised task: the training signal is just the text itself, no human labeling needed. This let training scale to nearly all of the public internet.
To predict the next token accurately across billions of diverse documents, the model is forced to internalize grammar, facts, reasoning patterns, and style as useful side effects, not as explicit goals.
Scale turned out to matter enormously. Bigger models trained on more data with more compute reliably get better, a relationship formalized in the scaling laws that guided the field's investment.
The genius of the approach is indirection: nobody had to hand-label "this is a good explanation of photosynthesis." The internet already contains millions of such explanations, and next-token prediction extracts the pattern for free.

How Inference Works

At inference time the model is a fixed function: feed in the tokens so far, get back a probability distribution over the entire vocabulary for the next token.
Generation is stochastic sampling, not deterministic lookup. A temperature parameter controls how sharply peaked the sampling is: low temperature picks the top candidate almost every time, higher temperature allows more variety and creativity.
This is why the same prompt can produce different outputs on different runs, and why LLMs can occasionally say something no one ever wrote verbatim: they're generating a plausible continuation, not retrieving a stored sentence.
Each generated token is appended to the context and fed back in, so generation is autoregressive: one token at a time, each conditioned on everything before it.
🔬 Deeper Look

Stage 1: Pretraining

Trains on a filtered, deduplicated crawl of the internet, roughly on the order of trillions of tokens, purely on next-token prediction with no notion of "conversation."
This is the most expensive stage by far, costing millions of dollars in compute and running for weeks to months on thousands of GPUs.
The output is a base model: a raw text completion engine that has absorbed world knowledge, language, and style, but has no concept of being an assistant, no sense of turn-taking, and no built-in helpfulness or safety behavior.
Ask a base model a question and it's just as likely to continue with more questions (mimicking a FAQ page) as it is to answer, because that's a statistically plausible continuation too.

Stage 2: Supervised Fine-Tuning

Human labelers (and increasingly, models assisting humans) write thousands of ideal conversation examples: a question paired with the exact helpful, honest answer wanted.
The base model is fine-tuned on this much smaller, much higher-quality dataset, which teaches it the format and persona of an assistant, not new knowledge.
This is where the model learns to follow instructions, adopt a consistent helpful voice, and structure answers, turning a raw completion engine into something that behaves like ChatGPT.
The resulting instruct / assistant model is what most people actually interact with; the underlying capability still comes from pretraining, SFT just reshapes how it's expressed.

Stage 3: Reinforcement Learning

The model is given practice problems (math, code, reasoning tasks with checkable answers) and generates many candidate solutions on its own.
Solutions that reach the correct answer are reinforced, making the token sequences that led there more likely in the future; wrong paths are discouraged.
This lets the model discover its own effective strategies for reasoning, rather than only imitating a human's written-out solution, which is often not how the model would naturally "think."
For open-ended tasks without a checkable answer, a reward model trained on human preference comparisons stands in for a grader, this is the RL part of RLHF.
⚙️ LLM Psychology

Hallucination

Hallucination happens because the model is trained to always produce a plausible-sounding continuation, and confidently fabricating an answer is often statistically indistinguishable, in training data, from confidently giving a correct one.
Early instruct models had no example in their SFT data that said "I don't know," so they never learned that response was even an option, they'd always generate something.
Modern mitigation: probe the model with questions about its own knowledge, and where it demonstrably doesn't know, add trained refusals ("I'm not sure") to the SFT data so it learns when to decline.
A stronger fix is tool use: instead of guessing from memory, the model learns to emit a search query, read real results, and ground its answer in retrieved text rather than parametric memory.

Knowledge & Memory Limits

Every model has a knowledge cutoff, the date its training data was collected. Anything after that is unknown unless surfaced through a tool like web browsing.
There is no persistent self or memory across conversations by default. Each chat starts from the same fixed weights, with no recollection of a prior session unless the product layer explicitly re-injects saved context.
The model has no continuous experience or introspective access to its own weights, when asked "how do you work," it answers from patterns in its training text about LLMs in general, not genuine self-knowledge.
This is why long-running "memory" features in chat products are a bolt-on: a separate retrieval system that reminds the model of past facts by stuffing them back into the prompt.

Jagged Capabilities

Capability is swiss-cheese: a model can solve graduate-level math yet fail a task a child would find trivial, like counting letters in a word. Strength in one area says little about strength nearby.
Every token costs roughly the same fixed amount of compute to produce, so the model cannot "think longer" about a hard sub-step within one token the way a human pauses. Multi-step arithmetic done in one shot often breaks for this reason.
Tokenization compounds this: the model never sees individual characters, it sees whole chunks (tokens), so counting letters or reversing a string requires reasoning about units it doesn't directly perceive.
The classic "strawberry" meme (models miscounting the R's) is exactly this: "strawberry" is a few opaque token chunks, not eight visible letters, so counting requires an indirect inference the model often gets wrong.
Mitigation in both cases is the same pattern as hallucination: let the model write out intermediate steps (more tokens = more compute spent) or call a tool (code interpreter) that does exact character-level or arithmetic work instead of guessing.
🎯 Applying It

Reasoning Models

Thinking / reasoning models (OpenAI's o-series, DeepSeek-R1) are produced by pushing the RL stage much further, rewarding the model for long chains of self-checking, backtracking text before the final answer.
The model learns, purely from reward signal, that generating more intermediate chain-of-thought tokens before answering raises the odds of a correct final answer, and RL amplifies that behavior over many training iterations.
DeepSeek-R1 notably showed this reasoning style can emerge from RL alone on verifiable problems, without needing humans to hand-write example reasoning traces first, a significant validation of the approach.
The trade-off is latency and cost: a reasoning model burns far more tokens (and money) per answer, so it's reserved for genuinely hard problems, not simple lookups or chit-chat.

Tool Use

Tool use extends the base capability rather than replacing it: the model is trained to recognize when its own parametric knowledge is insufficient or unreliable and emit a special action instead of an answer.
Web browsing lets the model pull in facts past its knowledge cutoff or verify claims against live sources, addressing the knowledge-cutoff and hallucination problems directly.
Code interpreter hands off exact computation, arithmetic, counting, data manipulation, to a real interpreter, sidestepping the fixed-per-token-compute weakness entirely.
Learning to use tools well is itself trained via the same SFT and RL pipeline: examples of good tool calls in SFT data, then reward for tool use that actually leads to correct answers in RL.

When To Trust vs Verify

Trust the model more for well-represented, stable knowledge (common programming patterns, well-known history) and trust it less for obscure facts, exact numbers, or anything post-cutoff.
For anything where being wrong is costly, prefer a workflow where the model cites sources or uses tools rather than answering purely from memory.
Treat confident tone as no signal of correctness; the model is equally fluent whether right or hallucinating, since fluency is the trained objective, not truthfulness per se.
For arithmetic, counting, or string manipulation, prefer asking the model to write and run code rather than compute directly, it will almost always be more accurate.
⚠️ Reliability

Failure Modes

Confident hallucination: fabricated facts, citations, or APIs stated with the same fluent tone as correct answers, especially on obscure or narrow topics under-represented in training data.
Reward hacking: in RLHF, the reward model is an imperfect proxy for real human preference, and enough RL optimization pressure will find ways to score well on the proxy without truly satisfying the user, for example padding answers or being sycophantic because that reads well to a reward model.
RLHF is not "real" RL in the game-playing sense: the reward model itself is a trained approximation, unlike a chess engine's ground-truth win/loss, so exploiting it too hard eventually degrades genuine quality even as the proxy score climbs, which is why RLHF runs are stopped early rather than optimized to convergence.
Prompt sensitivity: small rewordings can shift output quality noticeably, since the model has no stable internal "intent," only a response to the exact tokens given.

Where It Fits

Internet Text, then Pretraining, then Base Model, then SFT, then Assistant Model, then RL, then optionally a Reasoning Model.
Everything downstream, tokenization, embeddings, RAG, agents, tool use, is built on top of this base capability; the LLM is the reasoning engine that other systems orchestrate around.
Prompting, system messages, and few-shot examples all work by steering the existing learned distribution, they cannot add knowledge the pretraining never saw.
Understanding this pipeline explains most "weird" model behavior in practice: it's not a bug, it's the predictable result of which stage taught which behavior.

Real World Example

ChatGPT: GPT-4-class base model, SFT'd on curated conversations, then RLHF'd for helpfulness and safety, with an o-series reasoning variant for hard problems.
Claude: pretrained then fine-tuned with a Constitutional AI process, a variant of the RL stage that uses a set of written principles instead of only human preference labels to shape behavior.
DeepSeek-R1: notable for showing strong reasoning emerging largely from RL on verifiable math and code problems, at dramatically lower reported training cost than closed frontier labs.
Nearly every major assistant model on the market today follows this same three-stage arc, pretraining for raw capability, SFT for behavior, RL for refinement, differing mainly in data curation and RL details.
