📚 Few-Shot & Zero-Shot Learning

Teaching the model by example — and when no examples are needed at all.

📚 Core Concept

Zero-Shot, One-Shot, Few-Shot

Zero-shot: just ask, with no examples, relying entirely on the model's pretrained and instruction-tuned knowledge to infer what you want.
One-shot: a single example input/output pair before the real task, useful mainly to pin down format when one example is enough to disambiguate.
Few-shot: several (typically 2 to 10) example pairs before the real task, giving the model a pattern to imitate rather than just an instruction to follow.

Why Few-Shot Works

It works via in-context learning: the model infers the pattern, format, and style from the examples sitting in its context window, purely at inference time.
This is fundamentally different from fine-tuning: no weights are updated, nothing persists after the request, the "learning" is a temporary effect of what's currently in the prompt.
The model is doing pattern completion: given "here is the shape of five solved examples," it continues that shape onto a sixth, unsolved one.
Because nothing is stored, every single request has to re-pay the token cost of the examples, unlike fine-tuning where the cost is paid once upfront.

When Few-Shot Helps Most

Ambiguous output format: when there are many reasonable ways to structure a response and you need one specific shape, like a particular JSON schema or citation style.
Unusual task framing: tasks the model would not default to on its own, like a nonstandard summarization length or an invented category scheme.
Domain-specific style or jargon: internal terminology, legal boilerplate phrasing, or a company's specific voice that the model wouldn't produce by default.
Unusual label schemes in classification: when your categories don't map cleanly onto common-sense labels the model would guess at zero-shot.
🔬 Deeper Look

Diminishing Returns & Cost

Each example costs real tokens, both in latency and in API price, on every single request, not just once.
Too many examples can overfit the prompt: the model starts pattern-matching to the exact examples shown rather than generalizing the underlying task, especially if the examples are too similar to each other.
Past a small number of examples (often 3 to 8), additional examples usually add little accuracy gain for a lot of extra token cost, quality of examples matters far more than raw quantity.

Choosing Good Examples

Diverse: cover different variations of the task so the model generalizes the pattern instead of memorizing one narrow case.
Representative: reflect the real distribution of inputs the model will see in production, not just easy or convenient cases.
Correctly labeled: a single wrong example can actively teach the wrong pattern, since the model has no way to know it's an error.
Cover edge cases: include at least one tricky or boundary example, since models tend to default to the "average" behavior of the examples shown.
Bad examples are worse than no examples. A confidently wrong few-shot set will reliably steer the model toward the same mistakes.

Few-Shot vs Fine-Tuning

Few-shot is instant and cheap to set up, just edit the prompt, but it's bounded by the context window and re-paid on every request.
Fine-tuning is upfront-costly, a training run, data curation, an eval pass, but scales cheaper at high volume since the behavior is baked into the weights and costs nothing extra per request.
A common pattern: start with few-shot to validate the approach quickly and cheaply, then graduate to fine-tuning only once volume and stability justify the upfront investment.

🧩 Chain-of-Thought Few-Shot

Reasoning-Style Examples

Instead of showing just input and final output, chain-of-thought few-shot examples show the worked reasoning steps that lead to the answer.
This teaches the model not just what the answer looks like but how to arrive at it, which transfers better to problems that need multi-step logic rather than pure pattern lookup.
See the dedicated Chain-of-Thought page for the mechanics of why spreading reasoning across tokens improves accuracy, this is the few-shot flavor of that same idea.

Practical Notes

Reasoning examples cost more tokens per example than plain input/output pairs, so the diminishing-returns tradeoff is sharper, usually 2 to 4 worked examples is plenty.
Keep the reasoning style consistent across examples (same structure, same level of detail) so the model imitates a stable pattern rather than a mix of styles.
On modern instruction-tuned and reasoning models, zero-shot "think step by step" often gets most of this benefit without needing worked examples at all.

Where It Fits

Prompt Design, then choose zero-shot vs few-shot based on task ambiguity, then optionally add chain-of-thought structure to the examples, then send to the model.
Few-shot is a lightweight lever to pull before reaching for retrieval, tool use, or fine-tuning, it's often the fastest way to fix a format or style problem.
🎯 Applying It

Use Cases

Structured extraction: pinning down an exact JSON shape or field naming convention.
Classification with custom labels: categories specific to a business that the model wouldn't invent on its own.
Style transfer: matching a specific brand voice, code style, or formatting convention.
Rapid prototyping: validating a task is even feasible before investing in fine-tuning or a bigger pipeline.

Trade-offs

Context cost: examples eat into the token budget available for the actual task input, retrieved documents, or conversation history.
Overfitting to examples: too narrow a set of examples can make the model mimic surface details of the examples rather than the underlying task.
Maintenance: as the task evolves, the example set has to be kept in sync, stale examples can actively mislead.

When NOT to Use

When the task is already unambiguous and common (e.g. "translate this to French"), zero-shot is simpler and cheaper, added examples buy nothing.
When you have high volume and stable requirements, fine-tuning usually beats paying the few-shot token tax forever.
When examples would need to encode sensitive or proprietary data that shouldn't be repeated in every request's context.
Default to zero-shot first, add few-shot only when you observe a concrete format or style failure, and keep the example set as small as it can be while still fixing the problem.
