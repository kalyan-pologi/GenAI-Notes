Embeddings & Vector Search

🧠 Embeddings

Turning meaning into numbers, the foundation of semantic search and RAG.

🧠 Core Concept

What Is It

Vector representation of meaning: text, image, or other data turned into a list of numbers.
Each number is one coordinate in a high-dimensional space. The vector is a point, and the whole model is a map where position encodes meaning.
Similar meaning means close together in vector space, regardless of shared words. "How do I reset my password" and "I forgot my login" have zero words in common but land next to each other.
The individual dimensions are not human-readable. There is no "formality axis" you can point at; meaning is smeared across all 1536 numbers.

Why Introduced

Models need numbers, not raw text. Some encoding step is unavoidable.
The old answer was one-hot / bag-of-words: one slot per vocabulary word, 1 if present. A 50,000-word vocabulary gives a 50,000-long vector that is almost all zeros.
That encoding has two fatal flaws: it is sparse and huge, and every pair of distinct words is equally far apart. "cat" is exactly as unrelated to "kitten" as it is to "invoice".
Keyword search inherits the same flaw, which is why it fails on synonyms, paraphrase, and typos.
Solves the "meaning as distance" problem: dog and puppy should sit near each other, dog and spreadsheet should not. Embeddings make relatedness a measurable number instead of a lookup hit or miss.

How It Works

A transformer encoder reads the text and produces one vector per token, then a pooling step collapses them into a single fixed-length vector.
Training uses contrastive learning: show the model a query with its correct passage (the positive) plus many wrong passages (the negatives).
The loss (typically InfoNCE) pulls the query and positive together while pushing the negatives away. Repeat over millions of pairs and the geometry of the space becomes meaningful.
Hard negatives matter most: passages that look plausible but are wrong teach far more than random ones.
Training pairs come from naturally paired data: question and accepted answer, title and body, caption and image, translation pairs.
🔬 Deeper Look

Types of Embeddings

Word embeddings (older): word2vec, GloVe. One fixed vector per word, learned from co-occurrence statistics. No context, so "bank" in "river bank" and "bank account" gets the identical vector.
Contextual embeddings (BERT era): the same word gets a different vector depending on its sentence. This is what makes modern retrieval work on ambiguous language.
Sentence / chunk embeddings (current default): a whole passage becomes one vector. These are what you store in a vector DB.
Multimodal embeddings: text and images mapped into one shared space (CLIP style), so you can search photos with a text query.
Multi-vector / late interaction (ColBERT): keep one vector per token and match at token level. Much more accurate, much more storage.

Dimensionality & Cost

Dimension count is the main accuracy vs cost dial. More dimensions give the model more room to separate fine distinctions.
Returns diminish fast. Going 256 to 768 usually helps a lot; 1536 to 3072 often buys very little on ordinary corpora.
more dimsmore nuance
more dimsmore storage + slower search
1M chunks @ 1536~6 GB as float32
same, int8~1.5 GB
Many providers now offer variable dimension embeddings (Matryoshka style): the model is trained so the first N numbers are already a usable smaller embedding, so you can truncate 1536 to 512 and keep most of the quality.
Quantization (float32 to int8 or binary) is the other lever, cutting memory 4x to 32x for a few points of recall.

Relation to Tokenization

Text is first split into tokens (subword pieces), each mapped to a learned input vector.
The encoder contextualizes those token vectors, then pooling collapses them into one chunk-level embedding.
mean poolingaverage all token vectors
CLS poolinguse one special token
last-tokencommon in LLM-based encoders
Because pooling averages meaning, a chunk covering three unrelated topics produces a vector that sits between all three and matches none of them well. This is topic dilution.
This is why chunk size and boundaries matter so much for embedding quality. Aim for one coherent idea per chunk, roughly 200 to 500 tokens, with a little overlap so ideas are not cut mid-sentence.
⚙️ Practical Mechanics

Normalization & Distance

Most models return unit-length vectors already normalized to length 1. If yours does not, normalize before storing.
On normalized vectors, cosine similarity and dot product are the same ranking, so many DBs let you use the cheaper dot product.
Cosine ignores magnitude and compares direction only, which is what you want: a long document should not outrank a short one just for being long.
cosine1.0 identical, 0 unrelated
dot productsame order if normalized
euclideansmaller is closer
Absolute scores are not calibrated. Real-world corpora often score 0.7 to 0.85 for everything, so a fixed threshold like "keep above 0.8" transfers badly between models.
Pick the metric your vector DB index was built with, mixing them silently degrades recall. Tune thresholds per model on your own data, or just take top-k and re-rank.

Asymmetric Embedding

A short query and a long passage are different shapes of text. A question and its answer rarely look alike on the surface.
So many models are trained asymmetrically and expect a prefix or input type telling them which side they are encoding.
API styleinput_type="query" / "document"
E5 style"query: " / "passage: "
BGE styleinstruction prefix on queries only
Get it wrong and nothing errors. You just lose several points of recall, quietly, forever.
Symmetric tasks (dedup, clustering, similar-item lookup) compare like with like, so both sides use the same mode.
Forgetting this is one of the most common silent retrieval-quality bugs. Wrap the provider call in one helper that always sets the mode.

Batching, Limits & Caching

Embed in batches (dozens to hundreds per call) instead of one request per chunk. Network round-trips, not compute, dominate ingestion time.
Respect the model's max input tokens. Some APIs silently truncate instead of erroring, so the tail of a long chunk is dropped without warning.
Expect 429 rate limits on large backfills. Retry with exponential backoff and a concurrency cap.
Cache by content hash so unchanged chunks are never re-embedded. On a re-index of a mostly-unchanged corpus this saves nearly the entire bill.
Store the model name and version alongside every vector. Without it you cannot tell which rows need re-embedding after an upgrade.
Changing embedding model means re-embedding the whole corpus. Plan for a dual-write window: build the new index alongside the old, verify on your golden set, then cut over.
🧪 Choosing & Improving a Model

How to Choose

Start from a leaderboard (MTEB) but treat it as a shortlist, not an answer. Leaderboard corpora are generic; yours is not.
Shortlist three models, embed a few thousand of your own chunks, and score them on your own queries. This takes an afternoon and settles the question.

max context512 vs 8k token chunks
languagesEnglish-only vs multilingual
priceper million tokens, both passes
API (Voyage, OpenAI, Cohere): zero ops, best quality, but per-token cost and your text leaves the building.
Self-hosted (BGE, E5, Nomic, GTE): free at volume, data stays in-house, fully version-pinned, but you own the GPUs and the serving.
Cost has two sides: a one-time ingestion pass over the whole corpus, plus one small query embedding on every single search forever.

Measuring Quality

Build a small golden set: real user queries paired with the chunks that should have been retrieved. Mine them from support tickets or search logs.
Fifty to a hundred labeled queries is enough to rank candidate models confidently.
recall@kis the right chunk in the top k
MRR1 / rank of first correct hit
nDCGrank quality, graded relevance
recall@k is the metric that matters most for RAG: if the right chunk never enters the top k, no re-ranker and no LLM can recover it. Precision problems are fixable downstream, recall problems are not.
Run the golden set in CI. Chunking tweaks and prompt changes silently move retrieval quality.
Fifty labeled queries beats any leaderboard for your specific domain.

Improving Retrieval

Fix chunking first. It is free and usually the biggest win. Most "the embedding model is bad" complaints are really topic dilution from oversized chunks.
Contextual chunk headers: prepend the document title and section heading to each chunk before embedding, so an isolated paragraph carries its context into the vector.
Hybrid search: combine dense vectors with BM25 keyword scores, fused with Reciprocal Rank Fusion. Covers the exact-match cases dense retrieval misses (IDs, error codes, product names).
Re-rank: retrieve the top 50 cheaply, then score each against the query with a cross-encoder that reads query and passage together, and keep the top 5. Far more accurate than vector distance, too slow to run over the whole corpus.
Query rewriting: expand vague or pronoun-laden queries with an LLM before embedding, or generate a hypothetical answer and embed that instead (HyDE).
Fine-tune last. With a few thousand in-domain query and passage pairs you can beat any off-the-shelf model on your jargon, but it costs a training loop, an eval harness, and a re-embed of everything.
🎯 Applying It

Use Cases

Semantic search: find by meaning, so "cancel my plan" matches a doc titled "Terminating a subscription".
RAG retrieval: the standard way to pick which chunks get pasted into the LLM prompt.
Clustering and topic discovery: embed then run k-means or HDBSCAN to find themes in tickets or feedback with no labels.
Recommendations: "more like this" by nearest neighbors, and cold-start items work immediately since content, not history, drives the vector.
Deduplication: near-duplicate detection by high cosine similarity, catching reworded copies that hashing misses.
Classification: embed once, then a cheap logistic regression on top, or just compare to a few labeled examples. Far cheaper than an LLM call per item.
Guardrails and routing: match an incoming message against known jailbreak patterns or against intent examples to pick a handler.

Trade-offs

Lossy: a whole passage is compressed into a few thousand numbers, so fine nuance, negation, and numeric detail get blurred. "Refunds allowed" and "refunds not allowed" can sit uncomfortably close.
Model lock-in: vectors from different models (or even different versions) live in incompatible spaces and cannot be compared. Switching means re-embedding everything.
No exact matching: no guarantee on IDs, error codes, or verbatim strings. Dense retrieval is about resemblance, not equality.
Opaque: you get a score, never a reason. Debugging a bad result means eyeballing neighbors, not reading an explanation.
Ongoing cost: storage and compute per chunk, plus an extra network hop of latency on every query.

When NOT to Use

Exact or deterministic lookups (SKU, order ID, clause number): use a database index. It is faster, cheaper, and always correct.
Structured filtering ("orders over $500 last month"): that is SQL, not similarity. Use metadata filters, not vectors.
Small datasets: under a few hundred documents, keyword search or just putting everything in the prompt usually wins on both quality and simplicity.
Auditability requirements: when you must explain exactly why a document matched, keyword or rule-based retrieval is defensible and cosine distance is not.
Ultra low latency, uncached paths where an extra embedding API call blows the budget.
These are rarely either-or. The common production answer is hybrid: metadata filters narrow the set, then vectors rank what is left.
⚠️ Reliability

Failure Modes

Out-of-domain jargon embeds poorly. Legal, medical, and internal codenames were rare or absent in training, so the model has no real sense of where they belong. Project "Bluebird" lands near actual birds.
Missed exact matches: an error code or invoice number is exactly the query where dense retrieval is weakest and keyword search is strongest.
Negation blindness: "is X supported" and "X is not supported" are lexically and semantically near-identical to an embedder.
Silent version drift: a provider updates a model behind the same name and new vectors no longer align with the old ones. Quality decays with no error anywhere.
Topic dilution: bad chunking mixes unrelated concepts into one averaged vector that matches nothing well.
Prefix mismatch: queries embedded in document mode. No error, just quietly worse recall.
Mitigate with hybrid search (dense plus sparse), re-ranking, domain-tuned models, version-locking your embedding model, and a golden-set eval in CI so drift shows up as a failed build instead of a user complaint.

Where It Fits

Docs, then Chunking, then Embedding, then Vector DB, then Retrieval, then Re-rank, then LLM Context.
Embedding runs on both sides of the pipeline: once over the corpus at ingestion (batch, expensive, cacheable) and once per query at serve time (tiny, latency-critical).
Both sides must use the same model and version, or the query lands in a different space than the documents and results become noise.
Sits between raw ingestion and the retrieval layer, the translation step that makes semantic search possible. Quality here caps everything downstream: a chunk that is never retrieved cannot be re-ranked, and an answer the LLM never sees cannot be generated.

Real World Example

Voyage AI embeddings, used in Anthropic-oriented retrieval workflows, with domain variants (voyage-code, voyage-law, voyage-finance) tuned per vertical.
OpenAI text-embedding-3 (small and large), commonly stored in Pinecone, Chroma, or pgvector, and supporting dimension truncation.
Cohere embed, notable for strong multilingual coverage and int8 / binary compression modes.
Open-weight: BGE, E5, GTE, Nomic. Run locally via sentence-transformers or Ollama when data cannot leave your infrastructure.
A typical production stack: chunk to ~400 tokens with headers, embed with an API model, store in pgvector with metadata, retrieve top 50 hybrid, cross-encoder re-rank to top 5, then hand those to the LLM.
