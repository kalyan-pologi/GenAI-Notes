Foundations

📏 Context Window

The LLM's working memory — what fits, what doesn't, and how to manage it.

📏 Core Concept

What Is It

The context window is the total number of tokens a model can attend to at once: system prompt, conversation history, retrieved documents, and the room left for its own reply, all sharing one budget.
Think of it as working memory, not long-term memory. Nothing outside the window exists to the model at generation time, no matter how important it was three messages ago if it got pushed out.
Every part of a request competes for the same pool of tokens. A longer system prompt or a bigger retrieved chunk directly means less room for conversation history or output.

Why It's Finite

The core transformer mechanism, self-attention, compares every token to every other token, so naive compute and memory cost scale quadratically with sequence length. Doubling the context roughly quadruples the attention cost.
This made long context expensive and slow for years, which is why early models capped out at a few thousand tokens.
Modern models use engineering tricks (sparse attention patterns, sliding windows, better KV-cache management, architectural variants like grouped-query attention) to push the practical limit far higher without paying the full quadratic cost everywhere.
Even with those tricks, a bigger window still means more memory and latency per request. There is no free lunch, only a better trade curve.

Typical Sizes

Context limits have grown roughly two orders of magnitude in a few years: 4k tokens (early GPT-3 era) to 32k, then 128k, then 1M+ today.
Real numbers as of 2026: Claude models offer 200k standard with a 1M token beta tier, GPT-4 class models commonly ship 128k, and Gemini has pushed to 1M and experimentally 2M tokens.

🔬 Deeper Look

What Actually Fits

Rough rule of thumb: 1 token is about 0.75 English words, so 1,000 tokens is roughly 750 words, or about a page and a half of prose.
A 128k window is roughly a 250-page book. A 1M window is roughly a small codebase, several full novels, or thousands of pages of documentation.
1k tokens~750 words
128k tokens~250 pages
1M tokens~10 novels / mid codebase
Code tokenizes less efficiently than prose (punctuation, indentation, identifiers each cost tokens), so "fits in context" numbers for codebases are usually optimistic.

Context Window vs. Training Data

These are two completely different things people conflate constantly. The context window is what the model can see in this specific request. The knowledge cutoff is the date its training data ends, baked into the weights permanently.
A model with a 1M token context window and a January 2026 cutoff still knows nothing about events after that cutoff unless you paste that information into the context yourself.
Conversely, a huge context window does not expand what the model "knows" in general; it only expands how much you can hand it for this one conversation.
Large context is a bigger desk to work on, not a bigger library card.

Context Rot

Even within the technical limit, models do not attend to all positions equally well. This is often called context rot or the lost-in-the-middle effect: information at the very start or very end of the context is recalled more reliably than information buried in the middle.
Retrieval accuracy on a single fact can degrade noticeably as the context fills up, even for models explicitly benchmarked on long-context "needle in a haystack" tests.
Practical implication: do not assume that because something technically fits, the model will actually use it correctly. Critical instructions and key facts are safer near the start or end of the prompt.
💸 Cost & Latency

Compute Implications

More tokens in context means more compute for every forward pass, which means higher cost and higher latency, even if only the final output tokens change between requests.
Providers charge per input token, so re-sending a 100k-token conversation history on every turn of a long chat gets expensive fast, and it happens silently unless you are watching token counts.

Prompt Caching

Prompt caching lets a provider reuse the internal computation for a prefix of the prompt that has not changed between calls (a stable system prompt, a large document you keep referencing), billing that portion at a fraction of the normal rate on cache hits.
This is the main mitigation for the cost problem in long-context, high-repetition workflows like chat over a fixed document or an agent that reuses the same large tool definitions every turn.
Caching only helps when the cached prefix is byte-for-byte identical across calls; editing anything before the cached boundary invalidates it.

Practical Strategies

Start a new conversation to reset context once a chat has drifted far from the original topic or has accumulated a lot of dead weight, rather than letting it grow indefinitely.
RAG / retrieval as an alternative to stuffing everything in context: fetch only the relevant chunks for this query instead of pasting an entire knowledge base every time.
Summarize or compact long-running conversations periodically, replacing early turns with a condensed summary to free up budget while preserving the gist.
All three strategies exist because bigger context is not free, either in dollars, latency, or in how reliably the model actually uses what you gave it.
🎯 Applying It

When Large Context Helps

Genuinely useful when the task requires holistic understanding of a large artifact: reviewing an entire codebase for architecture issues, analyzing a full legal contract for cross-referencing clauses, or summarizing a long transcript where any part could matter.
Also useful for many-shot prompting, pasting in dozens of examples, or for multi-turn agentic workflows that need to remember many prior tool calls and results.
Reduces the engineering burden of building a retrieval pipeline for small-to-medium corpora that comfortably fit whole.

When It's a False Solution

Large context is not a substitute for relevance filtering. Dumping an entire wiki into the prompt and asking a narrow question wastes tokens, adds latency and cost, and can actually hurt accuracy versus handing the model just the two paragraphs that answer the question (see context rot).
"Just put it all in context" is a tempting shortcut that skips the actual engineering problem: figuring out what is relevant. It scales badly as the corpus grows past what any window can hold.
Retrieval systems also give you inspectability (you can see what was fetched and why) that "everything is in context somewhere" does not.

Where It Fits

The context window is the boundary between everything the application could show the model (documents, memory, tools, history) and what actually gets attended to on a given call. Retrieval, chunking, and summarization all exist to manage what crosses that boundary.
In an agentic loop, the context window fills with system prompt, tool definitions, conversation so far, and tool results, and each of those competes for the same fixed budget as the conversation grows across many turns.
Treat the context window as a scarce, expensive resource to curate, not a bottomless bucket to fill. The best long-context systems are the ones that put in the least irrelevant material, not the most.
