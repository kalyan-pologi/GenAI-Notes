🔤 Tokens & Tokenization

How text is split into chunks and why it matters for cost, context, and behavior.

🧠 Core Concept

What Tokens Are

A token is the basic unit an LLM actually reads and writes, a chunk of text somewhere between a character and a word, mapped to an integer ID from a fixed vocabulary.
Common words are often a single token ("the", "cat"), while rare words, made-up words, or non-English text get split into multiple sub-word pieces.
Before any neural computation happens, raw text is run through a tokenizer that converts it to a list of integers, and the model's embedding table looks up a vector for each ID, exactly the input format the network expects.
Everything the model perceives, generates, and pays for is measured in tokens, not characters or words, which is why token-level quirks show up everywhere in model behavior.

Why Not Raw Characters/Bytes

Feeding the model raw characters would keep the vocabulary tiny (about 100 symbols) but make every sequence extremely long, a short paragraph could become thousands of steps, and transformer compute grows quadratically with sequence length.
Feeding raw bytes has the same problem in a different guise: a small alphabet, but multi-byte UTF-8 characters and long sequences still blow up context usage.
Sub-word tokenization is the middle ground: a larger vocabulary (tens of thousands of entries) buys much shorter sequences, so more actual content fits in a fixed context window at a fixed compute budget.
This is a genuine trade-off dial, not a free lunch: push vocabulary size up and sequences get shorter but the embedding table and output layer get bigger and rarer tokens get less individual training signal.

How It's Learned: BPE

Byte Pair Encoding builds the vocabulary by starting from individual bytes and repeatedly merging the most frequent adjacent pair into one new token.
Run this process over a huge training corpus for tens of thousands of iterations, and each merge adds one entry to the vocabulary, common sequences like "ing" or "the" earn their own token, while rare combinations stay split into smaller pieces.
The result is a learned, data-driven vocabulary rather than a hand-built dictionary: frequent English morphemes get single tokens for free, while unusual strings fall back to shorter, more granular pieces.
Once trained, the same merge rules are applied at inference time to split any new text deterministically, the vocabulary itself doesn't change per request.

🔬 Deeper Look

Vocabulary in Practice

Modern production tokenizers sit around 100k to 200k entries, GPT-4's cl100k_base is about 100k, and newer tokenizers push toward 200k to cover more languages and code efficiently.
A bigger vocabulary generally makes non-English and code text more efficient by giving common foreign morphemes or code idioms their own tokens, instead of falling back to byte-level fragments.
Special reserved slots are carved out for control tokens (like end-of-text or role markers), so the practical text vocabulary is slightly smaller than the raw count.

Visible Model Weaknesses

The model cannot reliably count letters in a word because it never sees individual characters, "strawberry" might be 2-3 opaque token chunks, so counting R's requires indirect reasoning about sub-token content it wasn't trained to expose directly, the well-known strawberry meme.
Spelling and reversing strings are similarly hard: the model has to infer character-level structure from token identity rather than reading characters directly, a bit like being asked to spell a word using only its Morse code without ever seeing the letters.
Multi-digit arithmetic often breaks because numbers are tokenized inconsistently, "1234" might be one token in one context and split as "12"+"34" in another, so digit alignment for carrying and place value isn't guaranteed to be visible to the model.
These aren't reasoning failures so much as input representation failures, the model is working with the wrong granularity of information for the task.

Non-English Cost

Tokenizers are trained on corpora dominated by English, so English text gets efficient, near-word-length tokens while other languages fragment into many more, smaller pieces.
The same sentence in Hindi, Thai, or Japanese can take two to five times as many tokens as its English equivalent, purely because those scripts and morphologies were under-represented during BPE training.
Since pricing and context limits are per-token, this means non-English users effectively pay more and fit less content per dollar and per context window for equivalent content.
Newer tokenizers with larger, more multilingual-aware vocabularies (like GPT-4o's o200k) narrow this gap but rarely eliminate it entirely.
⚙️ Practical Mechanics

Conversation Structure

Chat models tokenize conversations using special reserved tokens that don't correspond to any real text, things like <|im_start|> and <|im_end|> mark where a turn begins and ends.
Role markers (system, user, assistant) are similarly encoded as dedicated tokens, so the model can distinguish "this is what the user said" from "this is what I should say next" purely from structure in the token stream.
This turns a multi-turn chat into one long flat token sequence with embedded structure, the model has no separate notion of "messages," it just sees a sequence shaped by these markers.
Because the format is baked in during SFT, a prompt that doesn't match the expected special-token structure (raw text pasted oddly) can degrade instruction-following, the model is pattern-matching to a format it was trained on.

Cost, Context, Latency

API pricing is per-token, typically quoted per million input and output tokens, so token count is the direct line item on your bill, not word count or character count.
Context windows are token limits: a "128k context" model truncates or rejects requests based on total tokens (prompt plus completion), not on some human-friendly measure like pages or words.
Generation latency scales with output tokens, since decoding is autoregressive and each token requires a full forward pass, longer answers are proportionally slower to produce, not just longer to read.

Prompting & Chunking Implications

When chunking documents for RAG, always measure and budget in tokens, not characters, since the actual tokenizer's chunk-to-token ratio varies by content type and language.
Dense, repetitive, or boilerplate text (code, tables, logs) can tokenize less efficiently than prose, so a "500 word chunk" of code may consume noticeably more tokens than 500 words of plain English.
When precision on exact characters matters (spelling, counting, parsing IDs), it's more reliable to ask the model to write and run code than to reason directly over tokens.
Keeping prompts and few-shot examples token-efficient matters doubly: it reduces cost and it leaves more of the context window for the content that actually needs to be there.
🎯 Applying It

Use Cases

Cost estimation: count tokens before sending a request to predict spend, especially important for high-volume batch pipelines.
Context budgeting: allocate a fixed token budget across system prompt, retrieved chunks, conversation history, and expected output before hitting the model's hard limit.
Chunk sizing for RAG: size document chunks in tokens (not characters) to match embedding model limits and keep retrieval units coherent.
Rate limiting and truncation logic: any system that needs to fit content into a fixed window (summarization, sliding context) has to reason in token units to be correct.

Trade-offs

Vocabulary size vs sequence length: bigger vocabulary shortens sequences and saves compute per document, but grows the embedding and output layers and dilutes training signal on rare tokens.
Efficiency vs interpretability: sub-word tokens are efficient for the model but opaque for humans debugging behavior, you can't just assume "one token equals one character or word" when reasoning about model quirks.
Fairness across languages: a shared vocabulary optimized for overall corpus frequency structurally advantages high-resource languages, correcting this fully would require deliberate multilingual balancing during tokenizer training.

When It Bites You

Silently truncated context: exceeding the token limit doesn't always error clearly, some APIs quietly drop the oldest content, producing confusing partial answers.
Underestimating cost for non-English or code-heavy workloads, since word-count-based estimates translate poorly to actual token counts for these content types.
Expecting character-level precision (exact counting, spelling, string reversal) directly from the model without accounting for the tokenization bottleneck, then being surprised when it's wrong.
Ignoring token overhead from conversation structure: special tokens, role markers, and system prompts all consume budget before any actual user content is counted.
⚠️ Reliability

Failure Modes

Inconsistent number tokenization: the same digit sequence can be split differently depending on surrounding context, undermining reliable arithmetic.
Boundary artifacts: tokens sometimes span a leading space or punctuation inconsistently (" the" vs "the" as different tokens), which can cause subtly different model behavior depending on exact whitespace.
Out-of-distribution strings (random IDs, hashes, rare unicode) fragment into many low-signal tokens, making the model's handling of them less reliable than ordinary prose.
Token-vs-word mismatch surprises: a request estimated at "under the limit" by word count can exceed it in tokens, especially for technical or non-English content.
Mitigate by always counting with the actual tokenizer (not word count), offloading exact character/number work to a code interpreter tool, and padding context budgets with margin for token-inefficient content.

Where It Fits

Raw Text, then Tokenization, then Embedding Lookup, then Transformer Layers, then Output Distribution, then Sampling.
Tokenization is the very first step in the pipeline, and every downstream limitation, from context windows to arithmetic mistakes, traces back to the granularity decided here.
It also directly underlies practical concerns elsewhere in the stack: embedding model input limits and LLM context windows are both expressed and enforced in tokens.
Nearly every "why did the model do that weird thing" question in practice resolves faster once you look at how the input actually got tokenized.

Real World Example

OpenAI's tiktoken library implements cl100k_base (GPT-4) and o200k_base (GPT-4o) BPE tokenizers, widely used to count tokens before sending API requests.
SentencePiece (used by Llama and others) is a similar sub-word tokenizer that also supports byte-fallback, so it can represent any input even for characters not seen during training.
The public OpenAI Tokenizer playground tool lets you paste text and see the exact token split and IDs, a quick way to sanity-check odd model behavior against actual tokenization.
A typical production habit: count tokens with the provider's real tokenizer library before every request, never estimate from word count, since the gap compounds at scale across cost, latency, and context limits.
