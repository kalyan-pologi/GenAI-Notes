Embeddings & Vector Search

🔍 Semantic Search

Finding content by meaning instead of exact keywords.

🧠 Core Concept

What Is It

Search based on meaning, not literal word matches. Two pieces of text with almost no words in common can still be judged highly relevant to each other.
Works by comparing query meaning to document meaning as vectors: both the search query and every candidate document are embedded into the same space, and relevance becomes a distance calculation instead of a string match.
Finds "terminate my subscription" when you search "cancel my plan," because both phrases land near each other in embedding space even though they share only one word.

Why Introduced

Classic keyword search (TF-IDF, BM25) scores documents by literal term overlap and term frequency. It's fast and precise, but it only knows about the exact words present, not what they mean.
Different wording for the same intent returns zero results with pure keyword search: a user searching "how to end my membership" gets nothing from a help doc titled "Cancelling your plan," even though a human would consider it a perfect match.
Solves the vocabulary mismatch problem between how users ask and how content is written, one of the oldest unsolved problems in information retrieval before embeddings became practical.

How It Works

Documents embedded once at ingestion time and stored in a vector database, this is a batch, upfront cost that doesn't repeat per query.
The query is embedded at search time with the same model used for the documents, producing a single vector that represents what the user is looking for.
The vector database finds the closest stored vectors to the query vector (typically by cosine similarity) and returns the corresponding documents as ranked top-k results.
🔬 Deeper Look

ANN Search

Comparing a query against millions of vectors one by one (brute-force / exact search) is mathematically simple but scales linearly with corpus size, which becomes too slow past a few hundred thousand vectors.
Approximate Nearest Neighbor (ANN) algorithms like HNSW (hierarchical navigable small world graphs) or IVF (inverted file index) build a structure that lets you find close matches in roughly logarithmic time instead of checking every vector.
These indexes trade a small amount of accuracy for a massive amount of speed, and that trade is almost always worth it since the difference between the true 1st and 3rd closest match is rarely meaningful to the end user.
Trade-off: approximate means occasionally missing the true closest match, in exchange for speed. Recall@k on these indexes is typically tunable, more accuracy costs more memory and latency.

Query vs Document Embedding

The query and the documents must be embedded with the exact same model and version, mixing models means the vectors don't share a coordinate system and distances become meaningless noise.

Some models use separate query and passage encoders trained together (asymmetric dual-encoder setups), since a short question and a long passage look structurally different even when they mean the same thing.

Result Ranking

Raw similarity score alone is not always "best," a document can be semantically close to the query but stale, low quality, or the wrong version of the right answer.
Production systems often combine similarity with recency, popularity, or business rules, boosting newer content, frequently-clicked results, or officially-endorsed sources over the raw vector distance ranking.
A re-ranking step, usually a cross-encoder that scores query and document together, can reorder the top candidates for relevance far more accurately than the initial retrieval pass, at the cost of being too slow to run over the whole corpus.
🎯 Applying It

Use Cases

Document and knowledge base search: internal wikis and help centers where users phrase questions differently than the docs are written.
FAQ and support bots: matching a user's free-form question to the closest pre-written answer without needing exact phrasing.
Product search: catching paraphrased or descriptive queries like "warm waterproof jacket" against a catalog that never uses those exact words.
The retrieval step inside RAG: fetching the passages that get stuffed into an LLM's context window before it generates an answer.
Code search and ticket deduplication: finding a function that does something similar, or a support ticket that's really the same underlying issue as one already filed.

Trade-offs

Can miss exact matches like order numbers or product codes, semantic similarity has no special respect for an exact string, so precise identifiers are actually its weak point.
Can retrieve results that sound related but are factually wrong, a passage about "refunds not allowed" can score close to a query about "refund policy" even though it says the opposite of what the user wants.
Quality depends entirely on the embedding model and chunking upstream, semantic search is only as good as the vectors it's built on, there is no independent correctness check built in.
No built-in sense of recency or authority unless explicitly added, an outdated document and a current one can look equally relevant to the vector index.

When NOT to Use

Exact lookups by ID, SKU, or known field: a database query with an index is faster, cheaper, and always correct where semantic search is probabilistic.
Small structured datasets where SQL filters already work, adding embeddings and a vector index is unnecessary complexity for a few hundred well-organized rows.
When you need fully deterministic, reproducible results, ANN search can return slightly different rankings across runs depending on the index implementation.
Very low latency needs without ANN infrastructure already in place, standing up and tuning a vector index has real setup and operational cost.
⚠️ Reliability

Failure Modes

Domain jargon poorly understood by a general embedding model, legal, medical, or internal terminology the model rarely saw during training embeds without real meaning.
Results too loosely related to be useful, when nothing in the corpus is a good match, the system still confidently returns its closest options rather than admitting no good result exists.
Missing exact keyword or ID matches, the exact scenario dense retrieval is structurally weakest at, since it's built entirely around approximate similarity, not exact string equality.
Index goes stale as new content is added, anything added to the source corpus after the last embedding/indexing pass is simply invisible to search until re-indexed.
Mitigate with hybrid search (combining dense vectors with keyword scores like BM25), cross-encoder re-ranking, domain-tuned embeddings, and incremental re-indexing so new content shows up quickly.

Where It Fits

Pipeline: Query, then Embed Query, then ANN Search over the Vector DB, then Top-K Results, then an optional Re-rank pass before results are shown or handed to an LLM.
The retrieval engine right after embeddings, turning "find things like this" into a ranked result set. It's the layer that makes RAG and modern search products possible, sitting between raw vectors and the user-facing answer.

Real World Example

Perplexity's search experience, which blends semantic retrieval with live web results and citations rather than relying on keyword indexes alone.
SaaS "AI search" features commonly backed by Pinecone, Weaviate, or pgvector, embedding a company's docs or product catalog once and serving semantic queries against it in production.
